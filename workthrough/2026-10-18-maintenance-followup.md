## 보류 항목 실측과 판단

### 새로 확인한 우선 과제: 기준값 부근의 경보 반복

리뷰에서 보류한 항목은 아니지만, 알림 피로를 살피다가 발견한 가장 큰 문제다.

- 최근 7일 사건은 53건이고, 그중 30건이 10-18 하루에 발생했다. 30건 가운데 MCP 합계 경보가 13건이었고, 7일 전체로는 53건 중 30건이 MCP 합계 경보였다.
- MCP 합계 경보 30건 중 26건은 메모리 압박이 없는 `review` 우선순위였다. 마지막 관측값은 대부분 5.00–5.03 GiB였고 기준은 5 GiB였다.
- 같은 경보가 해소된 뒤 1–2분 만에 다시 열린 경우가 반복됐다. 기준 아래 120초 유지로 해소가 확인된 직후 다시 기준을 넘고, 지속 확인을 거쳐 새 사건이 된다. 0.2.1의 B1 수정은 지속 확인 전 재초과만 막으므로 이 경우는 여전히 새 사건이다.
- 사건마다 4곳(푸시 기기·Gmail)으로 보낸다. 회복 알림도 켜져 있어, 1건이 최대 8회 알림이 된다(전달 기록 구조상 추정). 배포 후 3.6시간 동안에도 사건 5건이 열렸다.
- 권고: 해소 직후 30분 안에 같은 원인이 재발하면 이전 사건을 다시 활성화하고 새 발생 알림을 보내지 않는다. 회복 알림은 해소가 일정 시간 유지된 뒤에만 보낸다. 위험도 상승(critical)은 지금처럼 즉시 알린다.
- 대안은 해소 기준에 여유를 두는 방식(예: 기준의 95% 아래에서만 해소)이다. 이 방식은 Guard의 판정 자체를 바꾸므로 사건 단위 병합보다 영향 범위가 넓다.
- 규모는 중간이다(`incidents.reconcile`·전달 worker·회귀 검사). 실제 재발을 늦게 알리는 위험은 위험도 상승 즉시 알림으로 제한된다.

### E2 이력 조회 비용

- 리뷰 때의 정정: owner 실행 전 패키지 신뢰 검사(41개 경로)는 13ms로 병목이 아니다.
- 실제 비용은 다음과 같다(운영, 각 3회).

| 측정 항목 | 결과 |
|---|---|
| owner 조회의 프로세스 기동 고정 비용 | 0.3–0.6초 |
| 7일 이력 | 3.7–4.4초 |
| 14일 이력 | 4.0–4.6초 |
| 14일 구성(attribution) | 3.5–3.9초 |
| 세션 이력 | 2.8–3.0초 |
| 웹 API 재조회(컨트롤러 캐시 적중) | 0.03–0.07초 |

- 컨트롤러가 이 결과를 60초간 캐시한다. 화면 자동 갱신은 30초이므로, 14일 화면을 열어 두면 약 1분마다 이력과 구성을 합쳐 약 8초를 다시 계산한다.
- 이력 다운샘플의 모듈 캐시는 키에 호출 시각 기반 `since`가 들어 있어, 같은 프로세스 안에서도 적중하지 않음을 확인했다(2.0초 → 2.3초). 게다가 owner 조회는 매번 새 프로세스라 메모리 캐시가 유지되지도 않는다.
- 권고 1 (작음): 7일/14일의 컨트롤러 캐시를 5분으로 늘린다. 버킷이 30분/60분이라 표시 정확도에 사실상 영향이 없고 재계산이 1/5로 준다.
- 권고 2 (중간): 지난 날짜는 바뀌지 않으므로, 날짜별 집계를 owner 상태 디렉터리에 파일 캐시로 저장한다. 캐시 키에서 `since`를 빼고 첫 날만 별도로 처리한다. 첫 조회도 대부분 오늘 파일만 파싱하게 된다. owner가 자기 파일만 읽으므로 권한 경계는 바뀌지 않는다.
- 상시 owner 프로세스 도입은 권한 경계 변경이 크므로 권고하지 않는다.

### E3 드라이브 조회 시간 제한

- C/D/E는 모두 9p로 마운트되어 있고, 현재 `statvfs`는 즉시 응답한다. 응답 정지 사례는 관측되지 않았다.
- Guard 유닛에는 watchdog이 없다(`WatchdogUSec=0`). 드라이브 응답이 멈추면 표본 루프가 멈추고 알림도 멈춘다. 웹은 오래된 관측으로 표시하지만, 감시 중단 알림은 받을 수 없다.
- 권고 (작음, 보험 성격): 드라이브별 조회를 시간 제한이 있는 보조 스레드로 수행한다. 이전 조회가 아직 막혀 있으면 새 스레드를 만들지 않고 "응답 없음"으로 기록한다.

### F1 WSL 루트 파일시스템 경보 — 지금은 불필요

- WSL ext4는 1007G 중 330G 사용(35%)이다. 반면 VHDX 파일은 E:에 807GB이고, E:는 932G 중 여유 120G(약 13%)로 경고 기준 10%에 가깝다.
- VHDX가 놓인 E:가 ext4보다 훨씬 먼저 가득 차므로, 실제 위험은 기존 E: 드라이브 경보가 다룬다. 별도 루트 경보의 추가 가치는 낮다.
- 운영 참고: VHDX 크기(807GB)와 내부 사용량(330GB)의 차이가 크다. 화면의 "VHDX 정리 방법 보기"로 공간을 회수할 수 있다. 다만 실제 회수량은 보장되지 않는다.

### F3 "확인함" 시 재알림 중지 — 우선순위 낮음

- 정기 재알림은 warning이 6시간 넘게, critical이 15분 넘게 지속될 때만 간다. 7일간 6시간 넘게 지속된 warning은 2건, 15분 넘게 지속된 critical은 2건이었다.
- 알림 피로의 주원인은 재알림이 아니라 위의 반복 발생이다. 30분/1시간 보류도 이미 있다. 반복 발생 문제를 해결한 뒤 다시 판단한다.

### F2 로그 실시간 보기 — 선택

- 로그 창에는 이미 줄 수 선택, 필터, 자동 스크롤, 수동 새로고침이 있다.
- 권고: 창이 열려 있는 동안 5초마다 자동 새로고침하는 선택지를 둔다. 기존 조회 API를 그대로 쓰므로 새 권한 연산이 필요 없다. 규모가 작다.

### 그 밖

- 개요 사건 카드(F4): 0.2.1에서 진행 중 사건 수와 단일 사건 직접 연결을 넣었다. 별도 카드의 추가 가치는 낮다.
- SSE 배지 깜빡임(D16): 재현되지 않았다. 조치하지 않는다.
- 세션 2,000개 규모의 모바일 렌더링 약 10초: 운영 세션은 11개라 실사용 영향이 없다. 필요해질 때 다룬다.
- PSI 그래프 툴팁 브라우저 검사: 수정 전 코드에서도 25회 중 1회 실패하는 기존 간헐 실패다. 릴리스 게시를 막을 수 있으므로 검사 안정화를 권고한다.
