# 사용자 시나리오 중심 코드 리뷰 — 2026-10-09

검토 기준: `96c638b`의 로컬 main. 사용자의 요청은 상세 코드 리뷰와 테스트 환경에서의 사용 시나리오 검증이다. 제품 수정·운영 배포는 이번 범위에 포함하지 않는다.

후속 상태: 아래는 리뷰 당시의 결함 기록이다. 이후 [수정·확장 검증](2026-10-09-usability-remediation.md)을 진행했으며 연결된 진단 스크립트도 정상 동작을 요구하는 회귀 검사로 전환했다.

결론: 기존 검사는 통과했지만 새 실패·경합 시나리오에서 **P2 6건, P3 1건**을 재현했다. 설정 요청 유실, 잘못된 적용 완료 안내, 서로 다른 서비스 로그 혼합을 먼저 수정할 것을 권한다. 확인한 문제는 아직 제품 코드에 남아 있다.

## 검토 범위와 환경

- 웹의 데이터 갱신, 서비스 등록·제어·로그, 세션, 이력, 설정, 알림 UI를 중심으로 실제 호출 경로를 읽었다. `webapp.py`의 인증/CSRF/입력 검증, `service_control.py`의 설정 요청 저장·서비스 제어, `daemon.py`의 요청 적용 경로도 연결해서 확인했다.
- Python 3.14.4, Playwright 1.63.0, Chromium 153.0.8010.12. 기존 `.venv`를 사용했다.
- 실제 Chromium이 저장소의 HTML/CSS/JS와 CSP를 실행했다. `https://wrg.offline.test`의 요청은 전부 fixture로 처리했다. 설정 요청 유실 시험은 실제 Controller·daemon 함수를 임시 디렉터리에서 연결했고 서비스 명령 실행을 금지했다.
- 제품의 원격 서비스에 연결하거나 서비스/컨테이너/세션을 제어하지 않았다. 실제 Tailscale·Windows·외부 알림·WSL 부팅 검증으로 해석하면 안 된다. 모바일은 Chromium viewport 시험이며 실제 iOS/Safari·터치 키보드·스크린리더 검증은 아니다.
- 과거 리뷰의 해결 항목은 새 결함에 재집계하지 않았다. 전체 설치기·릴리스·의존성 보안 재감사도 이번 결과에 포함하지 않는다.

## U5 — P2: 조회 실패 후 이전 설정 결과로 적용 성공을 안내

위치: [app.js](../wsl_resource_guard/web/app.js) 1612–1629행, [service_control.py](../wsl_resource_guard/service_control.py) 270–279행.

1. 설정 화면에서 이전 `warning_available_gib = 6` 요청이 적용된 상태를 불러온다.
2. 새 값 `7`을 요청한다. POST는 새 ID로 접수됐다고 응답한다.
3. 뒤따르는 `/api/settings` 조회만 HTTP 502로 실패시킨다.
4. 화면 상단은 일부 갱신 실패이고 카드의 값은 6인데 성공 알림은 “warning_available_gib 변경을 적용했습니다.”가 된다.

`refresh()`는 실패를 알리고 정상 반환하므로 `settleConfigRequest()`가 이전 `settingsData.config_request.state === 'applied'`를 읽는다. 새 요청의 ID를 인수로 받지 않고, 상태 API도 ID를 노출하지 않는다. 사용자는 실제 임계값이 변경됐다고 믿고 화면을 떠날 수 있다. 설정 화면을 떠나면 `refresh()`가 현재 화면만 조회하는 구조도 같은 확인 경로의 제약이다. 화면 이동 변형은 코드로 확인했으며 이번 재현은 GET 실패 변형이다.

권고: POST ID를 보존하고 전용 상태 조회에서 동일 ID의 적용 결과만 인정한다. 통신 실패·대기·기한 초과·적용 실패·완료를 구분한다. 화면 이동과 무관하게 요청을 추적한다.

수용 기준: 새 요청 결과가 확인되지 않으면 성공 문구가 나오지 않는다. 이전 성공 캐시, GET 실패, 다른 요청 완료, 화면 이동을 각각 검증한다.

## U6 — P2: 빠르게 연속 변경한 설정 중 앞선 요청이 유실

위치: [service_control.py](../wsl_resource_guard/service_control.py) 264–268행, [daemon.py](../wsl_resource_guard/daemon.py) 923–955행.

1. `warning_available_gib = 6`을 요청하고 Guard의 다음 적용 전에 `email_heartbeat_minute = 30`도 요청한다.
2. 두 호출은 각기 다른 ID와 접수 메시지를 반환한다.
3. 실제 `apply_config_request()`를 실행하면 두 번째 ID만 적용된다. 다시 호출해도 첫 요청은 처리되지 않는다.
4. 임시 config에는 `email_heartbeat_minute = 30`만 있고 첫 번째 변경은 없다.

두 요청이 동일한 `config-request.json`을 교체한다. atomic replace는 파일 손상을 막지만 대기 요청을 보존하지 않는다. 동시에 실행할 필요도 없다. 현재 UI는 접수 후 창을 닫고 다른 설정 변경을 허용하므로 한 사용자의 연속 클릭이나 PC·모바일 병용에서도 가능하다.

권고: 대기 요청이 있으면 충돌을 명확히 반환하거나 ID별 큐를 둔다. 거부 정책이라면 대기 검사와 기록을 잠금 안에서 수행해야 한다. UI는 접수·대기·적용과 재시도 가능 시점을 표시한다.

수용 기준: 다음 수집 전 두 요청이 들어와도 둘 다 순서대로 적용되거나 두 번째가 명시적으로 거부된다. 접수 성공한 요청이 조용히 사라지지 않는다.

## U3 — P2: 늦은 응답이 다른 서비스의 대화상자를 덮어씀

위치: [app.js](../wsl_resource_guard/web/app.js) 2399–2412행, 2434–2436행.

- Demo 로그 요청을 보류하고 창을 닫은 후 Devin 로그를 연다. Devin 응답을 먼저 보내고 Demo 응답을 나중에 보내면 제목은 Devin Web인데 본문은 Demo 로그가 된다.
- 서비스 등록의 탐색 요청을 보류하고 창을 닫은 후 Demo 중지 확인창을 연다. 탐색 응답이 오면 제목은 Demo 중지인 채 등록 검색창으로 본문이 바뀌고 확인 버튼이 사라진다.

콜백이 시작 당시 창의 신원을 확인하지 않고 현재의 전역 `#log-content` 또는 `#dialog-content`를 찾아 쓴다. 오류 없이 잘못된 대상의 정보를 표시하므로 장애 진단에서 특히 혼란스럽다. 실제 다른 서비스에 제어 명령이 전달되는 것까지 확인한 결함은 아니다.

권고: 대화상자 세대 번호와 서비스 ID를 캡처하고 오래된 응답을 버린다. 닫을 때 읽기 요청을 취소하고, 같은 서비스의 줄 수 변경·새로고침 응답 역전도 처리한다.

수용 기준: A→B 로그 이동, 등록→작업 확인 이동에서 A의 응답이 B의 본문을 바꾸지 않는다. 로그 창을 다른 종류의 창으로 바꾼 뒤 응답해도 예외가 없어야 한다.

## U2 — P2: 한 API 지연이 전체 화면 갱신과 탐색 후 조회를 막음

위치: [app.js](../wsl_resource_guard/web/app.js) 201–217행, 1981–1988행, 2035행.

개요에서 디스크 응답만 보류했다. monitor/services는 이미 응답했지만 개요는 로딩 중이고 새로고침 버튼은 비활성이다. 서비스 화면으로 이동해도 새로운 서비스 조회가 시작되지 않는다. 디스크 응답을 해제한 뒤에야 갱신·탐색이 정상화됐다.

전체 `Promise.allSettled()`가 끝나야 setter를 적용하고 전역 `loading`을 해제한다. fetch에 애플리케이션 수준 timeout/취소가 없다. 따라서 독립적인 보조 데이터의 지연이 화면 전체를 막는다. 테스트에서는 응답을 짧게 보류해 인과관계를 확인했으며 실제 네트워크에서 무한히 지속됨을 측정한 것은 아니다. 브라우저/서버의 연결 종료 시점까지 기다릴 수 있는 구조다.

권고: 읽기 요청에 제한 시간·취소를 두고 섹션별로 준비된 결과를 렌더링한다. 다른 화면으로 이동하면 이전 조회와 독립적으로 요청한다. 변경 POST는 시간 초과 후 실제 적용 여부가 불명확하므로 자동 재전송 대신 상태 재확인이 필요하다.

수용 기준: 디스크가 응답하지 않아도 RAM·서비스를 볼 수 있고 다른 화면을 조회할 수 있다. 제한 시간 후 실패·재시도 안내가 나타난다.

## U1 — P2: 보조 데이터 실패가 정상 갱신/무기한 로딩으로 숨겨짐

위치: [app.js](../wsl_resource_guard/web/app.js) 887–892행, 2043–2057행.

현재 세션 조회는 성공시키고 `/api/session-history`만 HTTP 502로 실패시켰다. 세션 목록은 표시되지만 이력은 계속 “불러오는 중…”이다. 실패 알림은 없고 전체 상태는 “마지막 갱신”이다.

`sessionHistory`, `serviceMemory`, `dockerDf`, `overviewHistory`, `attribution`, `pushKey` 실패가 `failed` 집계에서 제외된다. 첫 실패에서는 로딩/빈 영역, 이전 성공 뒤 실패에서는 오래된 데이터를 최신 여부 표시 없이 유지할 수 있다. 이번 브라우저 재현은 첫 세션 이력 실패이며 나머지 항목은 같은 제외 분기에서 확인했다.

권고: 보조 기능이 전체 화면을 중단하지 않도록 유지하면서 섹션별 실패·마지막 성공 시각·재시도 버튼을 제공한다. 데이터 없음과 수집 실패를 구분한다.

수용 기준: 처음부터 502인 경우와 한 번 성공한 뒤 502인 경우 모두 해당 섹션이 명시적으로 실패/오래된 상태를 보여야 한다.

## U4 — P2: 서비스 등록 실패 후 수정해도 재시도 버튼이 복구되지 않음

위치: [app.js](../wsl_resource_guard/web/app.js) 2452–2472행.

등록 POST가 400을 반환하도록 한 뒤 접속 URL을 수정했다. 대화상자는 열린 채지만 해당 등록 버튼은 계속 비활성이다. catch/finally에서 `busyAction`만 해제하고 `b.disabled`를 복원하지 않는다. 배경 화면 갱신은 등록 대화상자를 다시 만들지 않는다.

사용자는 검색어를 바꿔 후보 목록을 다시 만들거나 대화상자를 닫았다 열어야 한다. 후자의 경우 표시 이름·URL을 다시 입력해야 한다. 오류도 대화상자 밖 공통 알림에 표시된다(U7).

권고: 실패 시 버튼을 복원하고 입력값을 보존한다. 진행 중에는 중복 등록도 차단하며 오류를 후보/폼 안에 표시한다.

수용 기준: URL 검증 실패와 일시적 503 뒤에 값을 고치거나 같은 값으로 재시도할 수 있고, 이미 진행 중인 요청이 중복 발송되지 않는다.

## U7 — P3: 설정 검증 오류가 열린 대화상자 밖에 표시됨

위치: [app.js](../wsl_resource_guard/web/app.js) 171–179행, 1608–1609행; [index.html](../wsl_resource_guard/web/index.html)의 `#notice`와 `#dialog` 배치.

heartbeat 분 입력에 60을 넣어 변경을 눌렀다. 오류는 modal 내부가 아닌 배경 `#notice`에 나타난다. 390px 실제 스크린샷에서 창 아래의 어두워진 영역에 보였고 입력창 곁에는 오류 설명이 없었다. dialog가 열려 있는 동안 배경 알림의 닫기 버튼도 직접 조작할 수 없다.

오류를 완전히 볼 수 없다고 일반화하지 않는다. 확인한 문제는 주 작업 영역 밖의 희미한 피드백, 입력과 오류의 연결 부재다. 실제 스크린리더 출력은 검사하지 않았다.

권고: 입력 바로 아래 오류 영역을 두고 `aria-invalid`, `aria-describedby`로 연결하며 문제 입력으로 초점을 돌린다. 성공·전역 상태는 기존 공통 알림을 유지한다.

수용 기준: 모바일·키보드 사용자가 대화상자를 닫지 않고 오류 원인과 수정 방법을 확인할 수 있다.

## 추가 사용성 개선 제안 — 확정 결함과 별도

- 설정 변경 안내의 “약 15초 안”은 고정 문구다. 수집 주기를 바꾼 사용자에게 실제 주기와 Guard의 최근 수집 시각을 함께 보여 주면 대기 원인을 이해하기 쉽다. 이번에 긴 주기의 end-to-end 적용 시간을 측정하지는 않았다.
- 오래된 세션 일괄 종료는 검색 결과가 아닌 전체 후보를 대상으로 한다. 확인창에 전체 대상이 명시되므로 숨겨진 오작동으로 분류하지 않는다. 다만 검색 중에는 “전체 오래된 후보”/“검색 결과” 범위를 버튼에 분명히 표시하면 오해를 줄인다.
- 비활성 서비스 조작의 이유가 `title`에만 있는 경우 모바일에서 찾기 어렵다. 상태 옆 설명이나 도움말로 같은 정보를 제공하는 것이 좋다.
- 소량 fixture의 반응성으로 대규모 서비스를 평가하지 않는다. 수백 개 서비스/장기 이력의 체감 성능, 실제 모바일 키보드/회전, iOS 홈 화면 Push는 후속 별도 시나리오로 남긴다.

## 실행 결과 및 재현 방법

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -s tests -q
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python tests/browser_offline.py
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python tests/browser_review_scenarios.py
node --check wsl_resource_guard/web/app.js
```

- 전체 단위 검사: 430개 실행, 428개 통과, 실제 root credential 전용 2개 skip. 일부 실패 fixture의 traceback/알림 실패 출력과 ResourceWarning이 있었으나 검사 결과는 OK였다. root 검사를 이번에 통과했다고 기록하지 않는다.
- 기존 offline browser suite: 통과. 최초 샌드박스 실행은 Chromium의 `Operation not permitted`로 실행 전 중단됐으며 허용된 제한 밖 실행에서 통과했다.
- 새 [진단 스크립트](../tests/browser_review_scenarios.py): 빈 데이터 30개 화면 조합과 3개 Escape 검사 통과. 결함 시나리오 7종×PC/모바일=14개와 설정 유실 1개를 재현했다. U3의 두 변형 때문에 7개 결함과 실행 조합 수는 다르다.
- 새 스크립트는 **결함 재현을 확인하는 assertion**이다. 성공 종료는 제품 수용 기준 통과를 뜻하지 않는다. 일반 unittest discovery와 CI에 추가하지 않았다. 수정 시 각 검사를 올바른 동작을 요구하는 회귀 검사로 전환해야 한다.
- 새 스크립트 작성 중 Path 대신 문자열을 전달한 fixture 오류와 빈 배열 응답의 Content-Type 누락을 보완했다. 이 두 실행 실패는 제품 결함으로 집계하지 않았다. 본문 결과는 보완 후 확인한 결과다.
- JS 구문·문서 상대 링크/공개정보·staged diff 검사 통과. 제품 코드 변경이 없어 운영 smoke·설치·외부 전송은 수행하지 않았다.

## 변경 및 마무리 범위

추가 변경은 이 기록, 재현 진단 스크립트, README의 알려진 제한 안내다. `docs/scenario-usability-review` 작업 브랜치에서 검증·커밋한 뒤 로컬 main에 병합하고 브랜치를 정리한다. 원격 push·운영 배포·제품 수정은 수행하지 않는다.

테스트 context와 임시 설정 디렉터리는 종료 시 정리됐다. 모바일 오류 화면 확인용 임시 스크린샷도 확인 후 삭제했으며 삭제 파일 링크는 없다. 기존 개발 `.venv`와 이번 작업 이전부터 있던 캐시는 보존한다. 최종 Git 상태·병합·정리 결과는 완료 응답에 보고한다.
