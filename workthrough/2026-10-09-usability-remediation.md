# 사용성 결함 수정 및 확장 검증 — 2026-10-09

기준: `60d391b`. [리뷰](2026-10-09-scenario-usability-review.md)의 U1–U7 수정, 작은 사용성 개선, 대규모 데이터·모바일 자동 검증을 수행한다. 설정은 한 건씩 적용한다. 운영 배포와 원격 push는 범위 밖이다. 실기기 확인은 자동화와 구분한다.

## 실행 기록

- 설정 요청의 연속/동시 덮어쓰기, 처리 결과 읽기 실패, 잘못된 요청 파일, Guard 중단·만료, ID별 조회와 오류 전파에 대한 8개 검사를 추가했다. 기존 코드에서 예상한 실패를 확인했다.
- Controller의 공유 작업 잠금 안에서 이전 결과 확인과 새 요청 저장을 묶었다. 처리되지 않은 요청은 409, 보관되지 않은 ID는 404, 처리 상태 읽기 오류는 503으로 전달한다. 기존 요청/결과 파일을 유지하고 ID·수집 주기·최근 Guard 관측 시각을 상태 API로 제공한다.
- 새 8개 검사와 기존 서비스 제어 74개·웹 29개·daemon 38개 검사 통과. 임시 소유자 디렉터리와 실제 Controller/daemon 함수를 사용했으며 운영 서비스 명령은 실행하지 않았다. UI 연결·전체 회귀·확장 검증은 이어서 수행한다.
- UI에 요청 ID 추적과 sessionStorage 복원을 연결했다. 서버 상태를 별도 조회해 화면 이동과 무관하게 확인하고, 이전/다른 요청 결과·조회 실패·404는 완료로 인정하지 않는다. Guard 수집 주기에 따른 대기/수동 확인 안내를 제공한다. 손상된 결과 JSON도 503으로 드러내는 검사를 추가했다.
- 조회를 섹션별로 적용하며 첫 실패·이전 데이터·마지막 성공 시각과 재시도를 표시한다. 읽기 30초/쓰기 130초 제한, 불필요한 이전 조회 취소, 같은 조회 공유, 요청별 중복 갱신 1회 예약을 연결했다. POST 결과 미확인은 자동 재전송하지 않고 명시적인 CSRF 거부만 1회 갱신/재시도한다.
- 대화상자와 로그 요청의 세대 번호를 대조해 이전 응답을 버린다. 등록 실패는 입력을 유지하고 버튼을 복구하며, 검색 중에도 중복 등록을 막는다. 설정 오류는 대화상자 안에 표시하고 aria 연결과 입력 초점을 유지한다. 비활성 서비스 버튼 설명과 일괄 종료의 전체 범위를 표시한다.
- Chromium·WebKit 각각 PC/모바일 상호작용 26개, 빈 데이터 30개 화면, Escape 3개와 모바일 회전/터치/제어된 visibility 이벤트 검사가 통과했다. 기존 Chromium offline suite도 통과했다. 모바일 오류 화면을 직접 확인했다. visibility 이벤트 검사는 실제 OS의 백그라운드 중단 검증이 아니다.
- 확장 검증에서 서비스 500개×288개 메모리 표본을 Math.max의 인수로 펼치다 `Maximum call stack size exceeded`가 발생했다. 같은 최대값을 순차 계산하도록 수정해 대규모 차트와 조작 검사를 통과했다. 대규모 렌더링의 시간 목표 초과는 별도 성능 제한으로 유지한다.
- 전체 단위 검사 439개 중 437개 통과, root credential 전용 2개 skip. JS 구문·actionlint·릴리스 관련 단위 5개 통과. fixture traceback과 기존 ResourceWarning은 실제 운영 오류나 추가 통과로 집계하지 않는다.

## API와 호환성

- `GET /api/settings/request?id=<16자리 소문자 hex ID>`: 동일 요청의 `pending/applied/failed`를 반환한다. ID 생략은 현재 요청, 현재 요청이 없으면 빈 객체다. `id`, `key`, `value`, `requested_at`, `interval_seconds`, `daemon_updated_at`, `state`, `message`를 제공한다.
- `/api/settings`의 기존 `config_request`에도 ID/수집 정보를 추가한다. 현재 요청과 마지막 처리 결과의 파일 구조는 유지하며 이전 파일에 새 필드가 없어도 읽는다. 완료 이력을 무제한 저장하는 큐/DB는 도입하지 않았다.
- 설정 대기는 `config_pending`/409, 조회할 ID가 없으면 `config_not_found`/404, 요청/결과 확인 실패는 `config_unavailable`/503이다. Unix 소켓부터 HTTP까지 허용된 코드만 전달한다. 잘못된 ID/값은 400, 기존 Tailscale·Origin·CSRF 경계는 유지한다.
- 요청 만료는 Guard가 처리한다. Controller가 시간 경과만 보고 대기 파일을 교체하지 않는다. 현재 요청보다 오래된 결과가 더 이상 보관되지 않으면 UI도 미확인으로 표시한다.

### 이력과 API 경로

실제 임시 JSONL을 생성하고 bounded streaming reader와 Flask → Controller → OwnerData 경로를 실행했다. Flask 인증 전달과 owner 실행 경계는 fixture이며 Gunicorn/Tailscale/실제 권한 전환의 왕복 지연은 아니다. 한 시간 공백을 주입하여 명목 개수와 실제 저장 개수를 구분했다. 두 입력 모두 335개 시간 bucket/92,822 byte로 집계됐고 마지막 critical과 PSI 미관측, 시간 공백을 보존했다.

## 검사 연결과 실행 제한

- 기존 브라우저 suite와 두 엔진의 사용성 회귀 검사를 CI에 연결했다. 규모 검사는 CI에서 `--iterations 1`로 기능을 확인하고 시간 목표 미달은 JSON에 기록한다. 이 최종 축소 명령도 API 경로를 포함해 로컬에서 exit 0으로 통과했다. `--iterations 20`은 p95 측정용이다. `.github` 설정을 로컬에서 actionlint로 검증했으며 원격 CI를 실행한 것은 아니다.
- 마지막 문구 보완은 조회 실패 때 `적용 여부 확인 필요 · 마지막 확인: 대기 중`으로 구분한다. 해당 시나리오를 두 엔진의 PC/모바일에서 다시 확인했다.
- 새 리뷰·수정 기록을 릴리스 allowlist에 포함해 README의 상대 링크가 압축본에서도 유지되도록 했다. 패키징 실물 검증 결과는 마무리 기록에 추가한다.
- WebKit은 OS 라이브러리가 없는 개발 환경이었다. 공식 Playwright 브라우저와 Ubuntu 패키지 78개를 임시 경로에 내려받아 추출했고 시스템 패키지나 서비스를 설치/변경하지 않았다. ldd와 x264 실제 로딩을 확인한 뒤, 시스템 ldconfig 캐시만 보는 사전 검사는 일회성 환경 변수로 생략했다. CI에는 이 우회를 넣지 않으며 일반 `install --with-deps`를 사용한다.
- WebKit fixture에서는 서비스 워커의 요청 우회를 막기 위해 worker를 차단한다. 기본 SSE fixture도 실제 서버의 polling-only 204로 보완했다. Push/worker 기존 검사와 실제 OS 알림 수신은 별도다.
- 초기 진단 중 대기 route의 정리 경고와 fixture의 SSE MIME/worker 우회 문제를 수정했다. 정리된 최종 Chromium·WebKit 회귀 실행에는 해당 callback 오류나 예상 밖 pageerror가 없다.

## 마무리 상태

U1–U7과 확장 시험에서 발견한 차트 오류를 수정했다. 대규모 성능 한계·실기기 미검증·운영 미배포는 위와 같이 유지한다. 최종 CI 축소 명령/패키징 확인, 문서 커밋과 main 병합·작업 브랜치 및 임시 자료 정리는 마무리 단계에서 기록한다.
