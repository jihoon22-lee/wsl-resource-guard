## 구현·검증 기록

변경 단위별 재현 실패, 수정 내용, 실제 검증 결과를 이 문서에 갱신한다. 외부 알림은 가짜 전송으로, HTTP 오류와 브라우저 검사는 격리된 대상으로 검증한다.

### R2 — 호스트 조회 전체 제한

실행 파일 존재 확인을 포함한 vmmem 조회 전체를 기존 단일 작업 제한 패턴으로 감쌌다. 15초를 넘기면 마지막 값·관측 시각과 새 시도 시각을 반환하며, 이전 작업이 아직 실행 중이면 추가로 시작하지 않는다. 실행 파일 확인과 실행 자체를 Event로 정지한 회귀 검사는 수정 전 모두 실패했고 수정 후 중복 방지·해제 후 정상 수집까지 통과했다. metrics 14개·disks 29개 통과. 전체 단위 503개 OK(root 전용 2 skip). 실제 Windows 파일시스템 장애는 유발하지 않았다.

### R3 — 실패·오래된 HTTP 결과 처리

HTTP 프로토콜 예외를 실패로 변환하고 서비스별 예외를 격리했다. 180초가 지난 결과와 미래 시각은 미확인으로 처리하며 systemd InvocationID·Compose 컨테이너 시작 시각이 바뀌면 이전 결과를 사용하지 않는다. 명시적 시작/중지/재시작에서도 캐시를 비운다. 화면과 요약은 실패·오래됨·미확인을 구분한다. 새 회귀 검사는 수정 전 5개 실패·2개 오류를 확인했고 수정 후 controller 87개와 전체 508개가 통과했다(root 전용 2 skip). Chromium 1440/390px에서 상태 표시·변경 요청 없음·JS 오류 없음을 확인했다. 전체 offline 검사는 T1 수정 후 다시 확인한다.

### R1 — 관측된 회복만 확정

해소 시각과 연속 정상 관측 확인 시간을 분리했다. PSI 일부/전체 미관측·디스크 실패·긴 공백·시계 역행·재초과 대기에서는 확인 시간을 다시 시작한다. 회복 확정 전 재발은 경과 시간과 관계없이 기존 사건·보류를 이어 가고, 정상 관측 30분 뒤 한 번 알린다. 기존 확정 기록은 재발송하지 않으며 새 필드가 없는 미확정 기록은 현재 관측부터 확인한다. 화면은 회복 알림 보류를 별도로 표시한다. 기존의 시계 역행 즉시 회복 검사는 새 관측을 요구하도록 계약을 바꿨고, 정상 확인 검사는 실제 연속 표본으로 보강했다. 수정 전 새 검사 6개 실패를 확인했다. 수정 후 전체 512개 OK(root 2 skip), JS 문법과 Chromium 1440/390px의 조치·재발/관측 보류 표시가 통과했다.

### R4 — 위험도 하락 시 보류 유지

표시용 위험도 전이와 알림 revision 증가를 분리했다. 하락과 낮은 위험도로의 재발은 기존 revision을 유지하고, 상승은 새 revision으로 즉시 알린다. 기본 수집 경로에서 1→3 GiB 개선을 보류 유무별로 확인했으며 두 경우 모두 기존 재알림 시각을 유지했다. 다시 1 GiB로 악화하면 즉시 알린다. 수정 전 새 검사 4개 실패, 수정 후 관련 46개와 전체 515개 OK(root 전용 2 skip)를 확인했다.

### R5 — 정기 이메일 전달 요약

사건 전달 파일이 없어도 정기 이메일 기록을 읽고, 두 경로의 시도·성공 시각과 오류를 합친다. 한 경로의 성공이 다른 경로의 실패를 가리지 않으며 경보 재알림 시계는 바꾸지 않는다. 정기 슬롯은 접수·실패·접수 미확인·발송 조건 미충족을 구분한다. 마지막 시도·성공은 다음 슬롯에도 보존하며 전송 중 중단된 슬롯은 중복 발송하지 않는다. 비공개 오류 문자열은 저장하지 않는다. 수정 전 9개 실패·3개 오류를 확인했고, 수정 후 정기 전달 6개와 전체 521개 OK(root 전용 2 skip)를 확인했다. 실제 이메일은 보내지 않았다.

### T1 — 현재 DOM의 카드 크기 검사

조회 완료를 기다린 뒤 연결된 모든 행의 이름·셀 크기를 한 번의 JavaScript 실행에서 측정한다. 실제 너비·넘침 검사는 유지하고 비어 있는 목록도 성공으로 넘기지 않는다. 전체 offline 검사에서 R3 변경 뒤 남은 문구 기대값을 갱신하고, 서비스 관리 창에서도 미확인과 실패가 구분되도록 보완했다. JS 문법·전체 offline 검사가 통과했고, 320/390/768px에서 Paseo 4개 상태를 각각 3회 반복한 36개 카드 검사도 통과했다.

### R6 — 수집 주기에 맞는 신선도

monitor와 실시간 summary가 서버의 `stale_after_seconds = max(60, interval_seconds × 3)`를 제공하고 개요·제목·배지가 이를 사용한다. 미래 시각도 사건 API와 동일하게 미확인으로 처리한다. 15/60/300/600초 주기의 정상·기한과 같은 경계·기한 초과·미래 시각을 서버와 1440/390px의 폴링·SSE에서 확인했다. 수정 전 API 16개 오류와 브라우저 경계 실패를 확인했고, 수정 후 전체 522개 OK(root 전용 2 skip), JS 문법·전체 offline 검사가 통과했다.

### R7 — 압축본 문서 링크 검증

Paseo 안내·0.2.3 릴리스 기록·이번 리뷰/수정 기록을 배포 허용 목록에 추가했다. 검증기는 압축 해제된 Markdown의 인라인·이미지·참조 링크를 실제 동봉 파일과 대조한다. URL·문서 내 anchor는 건너뛰고 상대 링크의 누락·압축본 밖 탈출은 거부한다. 해시 manifest 자체는 정상인 누락 문서 압축본도 실패하는 검사를 추가했다. 수정 전 7개 실패, 수정 후 release 8개 통과. 당시 Git 커밋 `4dffa40`으로 실제 압축본을 두 번 만들고 링크 검증·바이트 일치를 확인했다. 최종 0.2.4 압축본과 게시본은 버전 커밋 후 별도로 검증한다.

## 후속 요청에 따른 운영 배포

사용자의 명시적 운영 배포 요청에 따라 2026-10-23 19:48 KST에 0.2.3에서 0.2.4로 갱신했다. 검증한 GitHub Release 압축본을 다시 내려받아 SHA256SUMS와 manifest·문서 링크·CLI를 확인하고, 소유자도 읽을 수 있는 임시 배포 경로에서 정규 설치기를 웹/컨트롤러 → 시스템 Guard 순서로 실행했다. 두 설치기는 모두 성공했고 복구 백업을 생성했다.

- root 웹/컨트롤러와 owner CLI/Guard의 BUILD는 모두 `654f0959ba4adafd493968404c25583a915e53c7`, `version=0.2.4`, `dirty=false`다. `wrg --version`도 0.2.4다.
- 웹·컨트롤러·시스템 Guard는 모두 active/enabled이며 새 InvocationID로 실행된다. 새 Guard PID·시작 토큰과 일치하는 첫 상태 기록을 설치기가 확인했고, 이후 표본 갱신과 새 이력 저장도 별도로 확인했다.
- 사용자 설정·인증정보, 웹 접근 설정, 등록 정보, Push 키·구독 파일의 해시는 전후 동일하다. 등록 서비스 13개 중 별도 앱/기반 systemd 유닛 8개의 PID·InvocationID·NRestarts·실행/자동 실행 상태와 Compose 컨테이너 10개의 ID·상태·시작 시각도 모두 보존됐다. Paseo는 재시작되지 않았으며 HTTP·로컬·릴레이 검사 모두 정상이다.
- `wrg doctor`의 설치본 일치·시스템 Guard·컨트롤러·웹·Tailscale 검사가 통과했다. 기존 사용자 Guard 유닛은 설치돼 있으나 실행되지 않는다는 경고는 배포 전후 동일하다. 실제 감시는 시스템 Guard 한 개가 수행한다.
- loopback `/healthz`는 200, 인증 없는 관리 API는 403이다. 실제 Tailscale HTTPS의 monitor/incidents/services는 모두 200이며 최근 수집·사건 신선도와 60초 신선도 기한을 확인했다. 운영 웹 Chromium smoke에서 PC/390px 표시·전체 주요 화면·필터·자동/수동 새로고침·숨김 탭 중단·요청 중복 방지가 통과했다. 모바일 폭 검증은 실제 휴대전화 브라우저 시험과 구분한다.
- 확인용 알림을 한 번 보냈다. Gmail·Windows 알림 전송이 성공했고 등록 Push 구독 2개 모두 HTTP 201로 접수됐다. 이메일은 실제 받은편지함과 사용자 응답으로 수신을 확인했다. 사용자는 삼성 인터넷 휴대전화의 푸시가 도착하지 않았으며 이전 수신 경험도 확실하지 않다고 답했다. 따라서 휴대전화 푸시 수신은 미완료로 남긴다.
- 푸시 추가 점검에서 설치된 시스템 Python의 암호화·서명 등 7개 검사가 통과했고, 실제 HTTPS `/sw.js`는 설치본과 같은 내용을 200·no-store로 제공했다. 전송 코드·서비스 워커는 0.2.3 대비 변경이 없다. Android 구독에만 높은 우선순위·TTL 60초의 진단 푸시를 한 번 추가했고 HTTP 201 접수를 확인했다. 이것만으로 단말 미수신 원인은 확정할 수 없다. 삼성 인터넷의 현재 기기 등록 표시와 앱/사이트 알림 허용 상태를 확인한 뒤 재검증해야 한다.
- 배포 압축본·임시 소스·점검 스크립트·스크린샷을 제거했다. 설치/검증 로그와 전후 비교 기록은 owner 전용 배포 기록에, 복구 백업과 이전 실행 환경은 설치기의 원래 위치에 보존했다. 공개 저장소에는 개인 설정·주소·운영 데이터·로그·스크린샷을 포함하지 않았다. WSL 전체와 무관한 앱은 재시작하지 않았다.
