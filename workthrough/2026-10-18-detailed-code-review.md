## 버그

### B1 — P2: 짧은 재초과가 거짓 회복과 새 사건을 만든다 (재현)

- 위치: [daemon.py](../wsl_resource_guard/daemon.py) 275, 292, 899행; [incidents.py](../wsl_resource_guard/incidents.py) 143–157행.
- 데몬은 지속 확인 전(pending) 재초과를 "아직 회복 아님"으로 보고 이전 위험도를 유지하며 회복 시계를 되돌린다. 사건 저장소에는 지속 확인된 조건만 전달되어 pending 키가 보이지 않는다. 두 회복 시계가 따로 돈다.
- held Evaluation의 `conditions` 누락은 원인이 아니다. 그 분기는 평가 결과가 normal일 때만 진입하므로 원래 빈 목록이다.
- 기본 설정(회복 120초, 세션 경보 지속 120초) 시뮬레이션: 데몬은 계속 warning이었다. 사건은 t=1120 active → 1135 resolving → 1255 resolved(rev 2)였고, t=1270 새 id가 열렸다.
- 영향: 회복 알림 직후 같은 원인의 새 경보가 발송되고 사건 이력·보류 결정이 끊긴다.
- 권고: pending 조건 키를 사건 저장소에 전달해 기존 active/resolving 사건을 revision 변경 없이 유지한다.

### B2 — P2: 상위 세션 구성 변화가 재알림 간격과 보류를 무시한다 (재현)

- 위치: [incidents.py](../wsl_resource_guard/incidents.py) 55–62, 122–123행; [delivery.py](../wsl_resource_guard/delivery.py) 141–146행.
- RAM/PSI/swap/OOM 사건 대상은 상위 5개 세션, MCP 사건은 상위 8개다. 이 집합이 바뀌면 revision이 오르고 전달은 새 revision으로 모든 수신처에 재발송한다. 사건별 보류는 같은 revision에만 적용되므로 "30분 뒤 재확인"도 풀린다.
- 재현: RAM warning 중 세션 교체로 6시간 간격 대신 t=1030, 1210, 1510에 rev 1/2/3을 발송했다.
- [설정 문서](../docs/configuration.md)와 [사용 문서](../docs/usage.md)는 보류를 넘는 경우를 새 사건과 위험도 상승으로 설명한다.
- 권고: 대상 목록 변화는 내용만 갱신하고 revision을 올리지 않는다.

### B3 — P3: HEAD 요청으로 SSE 슬롯이 고갈된다 (재현)

- 위치: [webapp.py](../wsl_resource_guard/webapp.py) 204–234행.
- Flask는 GET 경로에 HEAD를 자동 추가한다. HEAD 응답은 본문 generator를 시작하지 않아 `finally`의 슬롯 반환이 실행되지 않는다.
- test client 재현: HEAD 2회 후 `GET /api/stream`이 204였다. 웹 프로세스 재시작 전까지 모든 탭이 폴링으로만 갱신된다.

### B4 — P3: Compose 로그의 비 UTF-8 출력이 조회 전체를 실패시킨다 (메커니즘 재현)

- 위치: [service_control.py](../wsl_resource_guard/service_control.py) 751행. 엄격한 텍스트 디코딩이고 환경 변수를 고정하지 않는다.
- 0xFF 바이트 출력에서 `UnicodeDecodeError`가 발생함을 확인했다.

### B5 — P3: 상태 점검이 HTTPError 응답을 닫지 않는다 (재현)

- 위치: [service_control.py](../wsl_resource_guard/service_control.py) 90행. 단위 검사 실행에서 `ResourceWarning: Implicitly cleaning up <HTTPError 403/503>`가 출력됐다.

### B6 — P3: 1시간 미만 경과 시간이 "0시간 1분"으로 표시된다 (코드)

- 위치: [app.js](../wsl_resource_guard/web/app.js)의 `age`. 같은 파일의 `durationText`는 1시간 미만을 분으로 표시한다.

### B7 — P3: 프로세스 트리 탐색에 순환 방지가 없다 (코드, 방어 보강)

- 위치: [processes.py](../wsl_resource_guard/processes.py) `descendants_of`. Guard의 사건 대상 설명 경로에서도 호출된다.
- PID 재사용으로 /proc 스냅샷이 불일치할 때만 이론적으로 순환이 생긴다. 발생하면 표본 루프가 멈추므로 방문 집합으로 막는다.

### E1 — P3: 전달 기록을 변화가 없어도 2초마다 fsync 저장한다 (코드)

- 위치: [delivery.py](../wsl_resource_guard/delivery.py) `tick` 마지막 저장. `updated_at`의 독자는 시계 역행 검사뿐이다.
- 권고: 내용이 바뀌었거나 일정 시간이 지났을 때만 저장한다.

## 효율·운영 관찰 (측정 후 결정)

- owner 조회마다 새 Python 프로세스와 패키지 전체 신뢰 검사를 수행한다. 그래서 이력 downsample·세션 스캔의 모듈 캐시가 운영에서 적중하지 않는다. downsample 캐시 키에도 호출마다 바뀌는 `since`가 들어 있다. 권한 경계 설계와 묶여 있어 운영 응답 시간을 측정한 뒤 디스크 캐시 등을 검토한다.
- Guard 표본 루프의 Windows 드라이브 `statvfs`에 시간 제한이 없다. 9p가 응답을 멈추면 감시도 멈출 수 있으나 관측 사례는 없다.

## 확인 후 제외

- `push_key`·`push_status`·조치 조회의 공용 잠금은 R6·U6 수정의 의도다.
- 설정 화면 렌더마다 푸시 등록 상태를 확인하는 요청은 R8 수정의 의도다.
- owner 신뢰 검사 결과 캐시는 권한 경계에 TOCTOU 위험을 만들므로 제안하지 않는다.
- held Evaluation의 `psi_alert` 누락은 `sample()`의 지역 값이 별도로 유지하므로 영향이 없다.

## 기능 제안 (사용자 결정 필요)

- WSL 루트 파일시스템 여유 공간 경보. 현재는 표시 전용이다.
- 서비스 로그 실시간 따라보기.
- "확인함" 선택 시 해당 revision의 정기 재알림 중지 선택지. 새 사건·위험도 상승은 계속 알린다.
- 드라이브 조회 시간 제한.
