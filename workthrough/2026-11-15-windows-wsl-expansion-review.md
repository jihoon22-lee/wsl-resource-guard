# 2026-11-15 상세 코드 리뷰와 Windows 확장 검토

## 범위와 결론

- 기준: `ec35ec0`, 버전 `0.2.4`. 시작 시 main과 작업 트리는 깨끗했다.
- 감시 루프·사건·전달·이력·설정·서비스 제어·웹·소유자 worker·CLI를 읽고, 운영 상태 파일(읽기 전용)과 대조했다. 이전 리뷰(10-08, 10-18, 10-23)에서 수정했거나 문서화한 항목은 다시 집계하지 않는다.
- 결과: 기능 결함 **P2 2건**, **P3 5건**, 구조·효율 개선 5건, 그리고 Windows 측 확장 방향이다. P0/P1은 없다.
- 이 작업은 리뷰다. 제품 코드와 테스트는 수정하지 않았다. 운영 서비스에 변경 요청을 보내지 않았고 Windows 측에는 조회 명령만 실행했다.
- 증거 구분: **재현**(임시 디렉터리·가짜 전송 함수), **운영**(실제 상태·전달 기록 조회), **실측**(조회 시간 측정), **코드**(정적 확인).

## 결함

### N1 — P2: WSL 재시작마다 디스크 경보가 새 사건으로 다시 열리고, 이전 사건은 거짓 회복 알림을 보낸다 (재현·운영)

**위치:** [incidents.py](../wsl_resource_guard/incidents.py) `_key`(56행), `reconcile`의 관측 공백·회복 분기(187–216행).

사건 키는 세션 사건을 제외하면 `원인:boot_id`다. Windows 드라이브 여유는 WSL 부팅과 무관하게 이어지는 상태인데도 boot ID가 바뀌면 다른 키가 된다. 재시작 뒤에는 다음 순서로 진행한다.

1. 같은 조건이 새 키로 열려 revision 1의 발생 알림을 다시 보낸다.
2. 이전 부팅의 사건은 현재 조건 목록에 없으므로 `unknown → resolving → resolved`로 넘어간다. `_unobserved()`는 드라이브가 조회되는지만 보므로 막지 못한다.
3. 30분 뒤 이전 사건이 "회복 확인" 알림을 보낸다. 디스크는 여전히 기준 미만이다.

**재현:** E: 여유를 9.3%(기준 10% 미만)로 고정하고 `evaluate → reconcile → Delivery.tick`을 연결했다. boot ID만 바꿨다.

```text
1000  active    disk.E  bootA  rev 1   발생 알림
5000  active    disk.E  bootB  rev 1   같은 상태의 발생 알림 재발송
6935  resolved  disk.E  bootA  rev 2   회복 확인 알림 (디스크는 계속 9.3%)
```

**운영 기록:** 11-14 재시작에서 같은 흐름이 남아 있다. 11-06에 열린 E: 사건은 재시작 2분 뒤(16:03) 해소 처리됐고 16:33에 5개 수신처로 회복 알림이 나갔다. 해소 판정 시점에 E:는 당시 기준 미만이었다(기준 변경은 16:07). 새 부팅의 E: 사건은 15:59에 따로 열렸다.

**영향:** 재시작할 때마다 지속 중인 디스크 경보가 "새 경보 + 회복"으로 한 번씩 더 온다. 사건별 보류·확인 기록도 끊긴다.

**수정 방향:** 부팅을 넘어 이어지는 자원(디스크)의 키에서 boot ID를 뺀다. RAM·PSI·swap·OOM은 부팅 범위가 맞다. 기존 저장 사건의 키 이전(같은 드라이브의 미해소 사건을 새 키로 승계)도 함께 처리해야 한다.

**추가 회귀 검사:** boot ID 변경 뒤 같은 디스크 사건 유지·무발송, 실제 회복 시 한 번만 회복 알림, 구 형식 키를 가진 저장소 읽기.

### N2 — P2: Windows 토스트 경로가 멈추면 모든 채널의 알림이 멈춘다 (재현)

**위치:** [notifications.py](../wsl_resource_guard/notifications.py) `_send_windows_toast`(129–156행), [delivery.py](../wsl_resource_guard/delivery.py) `tick`(195행).

0.2.4에서 호스트 메모리 조회는 `bounded_probe`로 감쌌지만 토스트는 그대로다. `/mnt/c`의 `Path.exists()`와 9p 실행 파일의 exec는 `subprocess`의 timeout이 시작되기 전에 멈출 수 있다. 전달 worker는 스레드 하나이므로 여기서 멈추면 Gmail·푸시를 포함한 이후 모든 전송이 중단된다.

**재현:** PowerShell 경로의 `exists()`만 Event로 대기시키고 사건 2건(토스트+webhook)을 넣었다. `tick()`은 5초 안에 끝나지 않았고 webhook 전송은 0건이었다. 해제하자 2건이 전송됐다. 실제 9p 장애를 유발하지는 않았다.

**수정 방향:** 토스트 전송 전체를 시간 제한이 있는 단일 실행 보조 작업으로 옮긴다. 아래 "Windows 확장"의 호스트 연결 모듈로 통합하는 편이 낫다.

### N3 — P3: 전송 실패 원인이 어디에도 남지 않는다 (운영·코드)

**위치:** [delivery.py](../wsl_resource_guard/delivery.py) 198–204행.

`tick()`은 채널이 돌려준 `result.detail`을 버리고 고정 문구("전송에 실패했습니다.")만 저장한다. 저널에도 출력하지 않는다. 운영 전달 기록에서 토스트 15건 중 6건이 3회 시도 뒤 실패했는데(시도당 약 10초), 원인을 확인할 방법이 없다.

**수정 방향:** 비밀값이 섞이지 않는 범위의 짧은 원인 코드(예: PowerShell 종료 코드와 정리된 오류 줄, HTTP 상태)를 전달 기록에 보관하고, 실패 전이 때 저널에 한 줄 남긴다.

### N4 — P3: VHDX가 호스트 드라이브를 채운 상황을 경보와 연결하지 않는다 (운영)

**위치:** [disks.py](../wsl_resource_guard/disks.py) `disk_insights`의 `vhd_reclaim_gib`(327–332행), `collect_disks`의 WSL 행.

운영 값은 다음과 같다. WSL ext4 사용 약 299 GiB, VHDX 파일 약 839 GiB, VHDX가 있는 E:의 여유 약 87 GiB(9.3%), WSL 화면의 여유 표시는 약 656 GiB(65%)다.

- E: 경보의 실제 원인은 약 540 GiB를 반환하지 않은 VHDX다. 화면에는 회수 가능 힌트만 있고 E: 사건의 원인·안내에는 나타나지 않는다. 결과적으로 운영에서는 디스크 기준을 5%/3%로 낮춰 경보를 없앴고, 이 값은 C:에도 같이 적용된다.
- WSL 디스크는 "표시 전용"이라 65% 여유로 보이지만, VHDX가 더 커져야 하는 쓰기는 호스트 여유 87 GiB에 막힌다. ext4가 이미 할당된 블록을 재사용하는 만큼 여유가 더 있으므로 정확한 한도는 아니다. 다만 두 값의 괴리는 표시되지 않는다.

**수정 방향:** 드라이브 사건에 "이 드라이브 사용량 중 WSL VHDX 비중과 회수 가능량"을 근거로 붙인다. WSL 행에는 호스트 드라이브 여유를 함께 표시하고, 회수 절차(sparse 설정 또는 종료 후 압축)를 문서로 안내한다. 자동 실행은 하지 않는다.

### N5 — P3: 디스크 기준이 전 드라이브 공통 백분율뿐이다 (운영·코드)

**위치:** [config.py](../wsl_resource_guard/config.py) `warning_disk_free_percent`·`critical_disk_free_percent`, [disks.py](../wsl_resource_guard/disks.py) `disk_severity`.

1 TB 드라이브의 10%는 약 93 GiB다. 대용량 데이터 드라이브에는 과하고 시스템 드라이브에는 적절한 값이 하나의 설정에 묶여 있다. N4의 운영 사례가 그 결과다.

**수정 방향:** 드라이브별 재정의 또는 "백분율과 절대 용량(GiB) 중 더 엄격하지 않은 쪽" 같은 절대 하한을 추가한다. CLI의 `C/D/E 경보` 고정 문구([cli.py](../wsl_resource_guard/cli.py) 251행)도 설정된 드라이브로 바꾼다.

### N6 — P3: Guard 자체의 정지를 알릴 경로가 없다 (운영·코드)

**위치:** [packaging/wsl-resource-guard.service](../packaging/wsl-resource-guard.service), [daemon.py](../wsl_resource_guard/daemon.py) `_run_locked`.

유닛에 `WatchdogSec`이 없다(운영 `WatchdogUSec=0`). 표본 루프가 멈추거나 WSL VM 전체가 내려가면 웹은 오래된 관측으로 표시하지만 알림은 오지 않는다. 정기 이메일이 유일한 생존 신호이고 기본값은 꺼짐이다.

**수정 방향:** `Type=notify`와 `WatchdogSec`으로 표본 완료마다 `WATCHDOG=1`을 보내 멈춘 루프를 재시작한다. VM 전체 정지는 WSL 안에서 감지할 수 없으므로 Windows 측 감시(3단계)가 필요하다.

### N7 — P3: 주간 리포트가 지정 요일에 꺼져 있으면 그 주는 건너뛴다 (코드)

**위치:** [daemon.py](../wsl_resource_guard/daemon.py) `weekly_report_slot`(975–984행). 지정 요일·시각 이후의 같은 날에만 발송한다. 개발 PC는 하루 종일 꺼져 있을 수 있다.

**수정 방향:** 같은 ISO 주 안에서 지정 시각이 지났고 미발송이면 발송한다.

## Windows 확장 검토

### 실측한 수집 가능 범위

WSL 안에서 interop으로 조회만 했다. 설치는 없다.

| 항목 | 방법 | 소요 |
|---|---|---|
| PowerShell 기동(빈 명령) | `powershell.exe -NoProfile` | 0.32초 |
| vmmem 작업 집합(현행) | `Get-Process vmmem*` | 0.52초 |
| 호스트 물리 메모리 전체·여유 | `Win32_OperatingSystem` | 0.69초 |
| 커밋 사용량·한도, 대기 캐시 | `Win32_PerfFormattedData_PerfOS_Memory` | 0.82초 |
| 페이지 파일 할당·사용·최고치 | `Win32_PageFileUsage` | 0.57초 |
| 고정 볼륨 전체(WSL에 마운트되지 않은 것 포함) | `[IO.DriveInfo]::GetDrives()` | 0.43초 |
| 메모리 상위 Windows 프로세스 | `Get-Process` 정렬 | 0.53초 |
| 배포판 목록·상태·버전 | `wsl.exe -l -v` | 0.09초 |
| 배포판별 VHDX 위치 | `HKCU:\...\Lxss` 레지스트리 | 0.43초 |
| `.wslconfig`의 memory·swap·autoMemoryReclaim | 파일 읽기 | — |
| GPU 메모리·사용률 | `/usr/lib/wsl/lib/nvidia-smi` (Linux 측) | — |
| CPU·IO 압력 | `/proc/pressure/cpu`, `io` (Linux 측) | — |

- 항목을 한 스크립트로 묶으면 PowerShell 기동은 한 번이다. 60–300초 주기라면 부담이 없다. `Get-Counter`는 3초가 걸려 제외한다.
- 운영 호스트에서 확인한 값의 예: 물리 메모리 약 32 GiB 중 여유 약 7 GiB, vmmem 작업 집합 약 12.4 GiB(WSL 내부 사용 약 5 GiB + 캐시 약 7 GiB), 커밋 40/100 GiB. WSL 안의 "가용 RAM 13 GiB"만으로는 호스트가 먼저 부족해지는 상황을 볼 수 없다.
- WSL에 마운트되지 않은 고정 볼륨이 하나 더 조회됐다. 현재 구조는 `/mnt/<문자>`의 `statvfs`만 보므로 감시 대상이 될 수 없다.

### 권장 단계

**1단계 — 호스트 관측(읽기 전용, 설치 없음).** 현재의 vmmem 조회를 "호스트 스냅샷"으로 일반화한다.

- 새 모듈 하나가 Windows 호출을 모두 맡는다: 실행 파일 위치 확인, 시간 제한, 단일 실행, 연속 실패 시 간격 확대, 출력 크기 제한, 고정 스크립트만 실행. 토스트(N2)와 doctor의 `.wslconfig`도 여기로 옮긴다.
- 스냅샷은 `metrics.host` 아래의 버전 있는 dict로 둔다(S5). 관측 시각·시도 시각·상태를 값과 함께 저장해 미관측을 0이나 정상으로 채우지 않는다. 이력은 본 이력 줄에 넣지 않고 낮은 주기의 별도 파일에 쓴다(S2).
- 수집은 소유자 Guard에서만 한다. root 컨트롤러는 Windows 실행 파일을 호출하지 않는다.
- 화면: 호스트 메모리(전체·여유·커밋), vmmem 대비 WSL 내부 사용량의 차이, 배포판 상태, `.wslconfig` 유효 한도, VHDX 자동 탐지(현재 `wsl_vhd_path` 수동 입력 대체), 고정 볼륨 전체.

**2단계 — 계층 간 판단.** 관측이 안정된 뒤 경보·안내에 연결한다.

- 호스트 가용 메모리·커밋 비율 경보. WSL 한도에는 여유가 있어도 호스트가 부족한 경우를 구분한다.
- vmmem과 WSL 사용량의 차이가 크면 캐시 반환 안내, VHDX 회수 가능량과 호스트 드라이브 경보 연결(N4), 드라이브별 기준(N5).
- Linux 측 보강: CPU·IO PSI, GPU 메모리, WSL 루트 파일시스템을 호스트 여유와 묶은 경보.
- Windows 프로세스는 표시만 한다. 종료 같은 제어는 넣지 않는다.

**3단계 — Windows 측 동반 구성요소.** WSL 안에서는 할 수 없는 일만 맡긴다.

- VM 전체 정지·Guard 무응답 감지: Guard가 남기는 생존 표식을 Windows 예약 작업이 확인해 Windows 알림을 보낸다(N6).
- 현재 문서로만 존재하는 Windows 로그온 작업을 저장소가 제공하는 설치·제거 스크립트로 표준화한다.
- 절전·재개, WSL 재시작 기록을 남겨 수집 공백의 원인을 설명한다.
- 권한 상승 없이 현재 사용자 범위에서 동작하게 하고, WSL로 들어오는 명령 경로는 기존의 제한된 연산만 사용한다.

**4단계 — 이름과 배포.** 1–2단계가 실제로 쓰인 뒤 `windows-wsl-resource-guard`로 바꾼다. CLI `wrg`, 설정·상태 경로, 유닛 이름은 유지하고 저장소 이름·문서·패키지 메타데이터부터 바꾼다. 경로까지 바꾸려면 설치기의 이전 절차가 따로 필요하다.

### 먼저 정할 것

- 1단계의 호스트 스냅샷 주기 기본값(권장 60초, 현행 vmmem은 300초).
- Windows 프로세스 이름을 이력·알림에 남길지 여부. 권장은 화면 표시만 하고 저장하지 않는 것이다.
- 3단계의 Windows 측 구현 언어. 권장은 추가 런타임이 없는 PowerShell 스크립트와 예약 작업이다.

## 구현 언어 검토 (Python 유지 대 Go·Rust 전환)

리뷰 뒤 "이 기회에 백엔드를 Rust나 Go로 바꾸는 것"을 검토했다. 판단 근거로 운영 유닛을 추가 실측했다(가동 약 28.6시간, cgroup 기준이라 자식 프로세스를 포함한다).

| 유닛 | 현재 메모리 | 최고 메모리 | 평균 CPU |
|---|---|---|---|
| Guard | 약 35 MiB | 약 38 MiB | 0.48% 코어 |
| 서비스 컨트롤러 | 약 89 MiB | 약 193 MiB | 3.7% 코어 |
| 웹 | 약 23 MiB | 약 55 MiB | 0.02% 코어 |

- 컨트롤러 cgroup의 최고 메모리는 유닛의 `MemoryHigh=192M`에 도달했다. CPU도 Guard의 약 7.6배다. 컨트롤러는 소유자 조회마다 Python 프로세스를 새로 띄우고(임포트만 0.08초·26 MiB, 10-18 실측으로는 조회당 0.3–0.6초), 상태 조회마다 `systemctl`·`docker`를 실행한다. 화면이 열려 있으면 요약 조회가 3초마다 반복된다. 원인별 비중은 측정하지 않았다.
- 수집 안정성 문제는 언어와 무관했다. 이번 N1·N2와 이전 리뷰의 결함은 모두 사건 식별 범위, 미관측과 정상의 구분, 9p·PowerShell 경계의 시간 제한 같은 설계 문제다. 커널에서 멈춘 9p 호출은 어느 언어에서도 스레드 하나를 붙잡는다.
- 호스트 수집의 비용은 PowerShell 기동(0.3초 이상)이고 호출하는 쪽 언어와 무관하다.

**권고:** 전면 재작성은 하지 않는다. 컴파일 언어는 효과가 실측으로 뒷받침되는 두 곳에만 순서대로 도입한다.

1. Windows 측 동반 구성요소(3단계)를 새로 만들 때 Go 단일 실행 파일을 검토한다. Windows에 런타임을 설치하지 않아도 되고, PowerShell 없이 Win32 API로 호스트 값을 읽으면 조회당 기동 비용이 준다. 서명되지 않은 실행 파일에 대한 Windows 보안 기능의 반응은 확인이 필요하다.
2. 그다음 후보는 소유자 worker와 컨트롤러다. 프로세스 기동이 수 밀리초가 되면 "조회마다 권한을 내린 새 프로세스"라는 현재의 경계를 유지하면서 위 CPU·메모리 비용이 줄어든다. 웹 가상환경과 uv 설치 경로도 없앨 수 있다.
3. Guard는 마지막이다. 자원 사용이 이미 작고 표준 라이브러리만 쓴다.

- Go를 Rust보다 권한다. 표준 라이브러리만으로 HTTP·TLS·SMTP·JSON·ECDH·AES-GCM을 다룰 수 있어 현재의 "런타임 의존성 없음"을 유지하기 쉽고, WSL에서 Windows용으로 교차 빌드하기 쉽다. Rust는 메모리 사용이 더 작고 상태 전이를 타입으로 강제할 수 있지만, 같은 범위에 외부 crate가 여럿 필요하고 작성·검토 비용이 크다.
- 전환 비용: Python 약 10,000행과 검사 약 12,000행(단위 560개), pidfd·SO_PEERCRED·권한 강하 같은 경계 동작의 재검증, 소스 압축본 배포에서 바이너리 빌드·배포로의 전환.
- 선행 조건: `state.json`·`incidents.json`·컨트롤러 소켓 요청의 형식을 문서화하고 버전을 붙인다. 그래야 구성요소를 하나씩 바꿀 수 있다. S2(날짜별 집계)와 N1·N2는 언어와 무관하게 먼저 고친다.

## 권장 처리 순서

1. N1(거짓 회복·중복 알림)과 N2(알림 전체 중단) — 알림 신뢰성에 직접 영향을 준다.
2. N3(실패 원인 보관) — N2를 고치면서 같이 처리한다.
3. 호스트 연결 모듈과 1단계 관측 — N2·S5를 흡수한다.
4. N4·N5(디스크 판단)와 2단계.
5. S1·S2·S3 구조 정리는 위 변경과 겹치는 부분부터, N6·N7과 3단계는 그 뒤.

## 검증 한계

- 브라우저 검사(`browser_offline.py` 등)와 Gunicorn 전송 검사는 이번에 실행하지 않았다. 프런트엔드는 구조만 확인했고 화면 결함은 새로 찾지 않았다.
- N2는 정지 주입으로 확인한 경로다. 실제 9p 정지의 발생 빈도는 측정하지 않았다. 토스트 실패 6건의 실제 원인은 기록이 없어 확인하지 못했다(N3).
- N4의 "실질 여유"는 ext4의 블록 재사용에 따라 달라지는 추정이다.
- Windows 조회 시간은 한 호스트에서 한 번씩 잰 값이다. 호스트가 바쁠 때의 분포는 측정하지 않았다.
- N1–N7과 S1–S5는 모두 미수정이다.
