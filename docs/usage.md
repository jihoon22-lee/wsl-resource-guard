# 사용법

```bash
wrg status
wrg top
wrg sessions --projects
wrg sessions --stale
wrg mcp
wrg disks
wrg history --hours 24
wrg history --episodes
wrg weekly-report  # 미리보기; --send는 실제 발송
```

웹의 개요는 최신 자원·경보·서비스 상태를 보여 줍니다. 세션·MCP·이력·디스크 화면은 같은 수집 데이터를 사용합니다.
수집 실패와 오래된 관측, 실제 숫자 0을 구분해서 확인하세요. 실시간 연결이 끊기면 최신 조회 결과를 사용하며, 오래된 관측은 현재 정상으로 표시하지 않습니다. PC의 그래프 hover와 모바일 tap으로 상세 값을 볼 수 있습니다.

조회는 받은 영역부터 표시합니다. 일부 조회가 실패하면 해당 영역의 오류와 마지막 성공 시각을 확인하고 `다시 시도`를 누르세요. 이전 값을 유지하는 경우 `이전 값`으로 표시하며, 화면 이동과 이력 기간 변경은 다른 조회의 완료를 기다리지 않습니다.

## 휴대전화 푸시·Gmail에서 경보 확인

알림의 `원인과 영향 확인`을 열면 해당 경보 사건으로 이동합니다. Tailscale이 연결돼 있어야 하며 연결을 복구한 뒤에는 메일의 같은 링크를 다시 여세요. Samsung Internet의 일반 탭에서 사용할 수 있고 실제 수신은 Android와 사이트 알림 권한·기기 상태에 영향을 받습니다.

1. 발생 시각과 최근 관측, 현재 지속/회복 확인/해소/미확인을 구분합니다. 오래된 알림이 현재도 같은 상태라는 뜻은 아닙니다.
2. 현재 값·기준값·첫 관측 대비 변화와 가용 RAM·PSI를 확인합니다. 높은 점유량만으로 누수나 종료 필요성을 단정하지 않습니다.
3. 관련 대상의 `실제 작업과 중단 영향 확인`을 엽니다. 공용 앱 서버는 여러 프로젝트를 포함할 수 있습니다. 위치·프로젝트·명시적 작업 ID·확인 가능한 제목과 영향을 보여 줍니다.
4. 사용 중이면 `작업 중 · 확인함`, 나중에 확인하려면 사건별 30분/1시간 보류를 선택합니다. 확인과 보류는 해결 처리와 다르며 새 사건과 위험도 상승은 계속 알립니다.
5. 개별 도구는 프로젝트·도구 이름으로 찾고 영향 범위를 확인합니다. 제목·현재 진행 여부·저장/재개 가능성이 미확인이면 원래 앱에서도 확인하세요.

Gmail과 푸시의 전송 서버 접수는 실제 수신 증거가 아닙니다. 상세 화면에서 기기/수신처별 대기·접수·실패·접수 미확인을 확인합니다. 전송 응답이 끊겨 접수 여부가 불명확하면 중복 이메일을 피하기 위해 자동 재전송하지 않습니다.

보관 기간이나 표시 한도로 사건이 없어지면 다른 PID로 연결하지 않고 기록이 없음을 표시합니다. PC/WSL 자체가 꺼지면 내부 감시기는 새 알림을 보낼 수 없습니다.

## 웹 설정 변경

숫자 설정은 한 건씩 적용합니다. 접수 후 Guard가 다음 측정에서 검증하며, 대기 표시에서 설정 이름·값·수집 주기·최근 수집 시각을 확인할 수 있습니다. 대기 중에는 다른 변경을 접수하지 않습니다.

화면 이동과 같은 탭의 새로고침 후에도 요청 ID로 처리 결과를 확인합니다. 적용 여부를 조회하지 못한 상태를 성공으로 표시하지 않습니다. 자동 확인 시간이 지나면 `상태 다시 확인`을 누르세요. 새 탭에서는 설정 화면의 현재 대기 요청을 확인할 수 있습니다.

서버는 현재 요청과 마지막 처리 결과를 보관하므로, 이후 변경이 이어진 오래된 ID는 조회할 수 없을 수 있습니다. `적용 여부 확인 필요`가 나오면 현재 설정값을 확인하세요. Guard가 중단되면 다른 설정으로 덮어쓰지 않고, 재개 후 기존 요청의 적용 또는 만료 처리를 기다립니다.

## 서비스 관리

`wrg services` 대화형 메뉴 또는 웹에서 현재 발견되는 systemd·Compose 서비스를 등록합니다.
기존 서비스의 프로그램·환경 파일·DB를 가져와 재배포하지 않습니다.

- 시작·중지·재시작: 현재 실행 상태 변경
- 자동 실행 켜기·끄기: 부팅 시 동작 설정
- 사용·미사용: 실행과 자동 실행을 함께 조정
- 등록 삭제: Resource Guard 관리 목록에서 제거. 외부 앱 데이터는 보존

기반 서비스 변경은 다른 앱에 영향을 줄 수 있습니다. Tailscale 연결을 끊는 연산은 웹에서 제한합니다.
등록 오류는 대화상자 안에 표시하며 이름·URL을 수정해 다시 시도할 수 있습니다. 변경 요청의 응답이 끊기거나 시간을 초과하면 이미 적용됐을 수 있으므로 현재 상태를 먼저 확인하세요. 화면은 이를 자동 재전송하지 않습니다.
OpenCode 보조 로그를 읽지 못하면 해당 오류와 정상 journal을 함께 표시합니다. 요청 줄 수 외에 응답 크기 상한도 적용되므로 큰 로그는 일부만 표시될 수 있습니다.
oneshot 서비스의 `active (exited)`는 실행 프로세스가 계속 존재한다는 뜻이 아닙니다.
추가 앱 유닛은 packaging/examples의 템플릿을 참고하되 설치 경로와 앱 자체 보안 정책을 직접 확인합니다.

## 세션 종료

```bash
wrg stop <pid> --confirm
wrg stop-mcp <pid> --confirm
```

PID·시작 시각·소유자·대상 분류를 다시 검증합니다. systemd 관리 서비스는 서비스 화면에서, 여러 작업의 공용 실행기는 원래 앱에서 작업별로 중지합니다. 웹의 오래된 세션 일괄 종료는 제공하지 않습니다. 실행 시간이 길거나 CPU가 낮다는 사실만으로 불필요한 작업이 되는 것은 아닙니다.

웹에서는 `작업·영향 확인` → `종료 영향 미리보기` → 영향 동의 → `확인한 대상 종료 요청` 순서로 진행합니다. 미리보기는 120초 동안 유효하고 실행 직전에 신원·프로젝트/명령·자식 구성과 명시적 작업 ID를 다시 대조합니다. 변경됐으면 실행하지 않고 다시 확인하게 합니다.

신호는 pidfd로 고정한 대상에 소유자 권한으로 전달합니다. 커널/Python이 이를 지원하지 않으면 종료 기능을 거부합니다. SIGTERM을 보냈다는 표시가 실제 종료를 뜻하지 않으며 남은 자식 프로세스와 일부 실패를 별도로 확인합니다. RSS는 공유 메모리가 중복될 수 있는 점유량이며 같은 양의 RAM 회수를 약속하지 않습니다.

응답 유실·화면 잠금·새로고침 후에는 같은 조치 URL의 `저장된 결과 다시 확인`을 사용하세요. 같은 조치 ID는 신호를 다시 보내지 않습니다. 종료 뒤에는 `경보 해소 여부 확인`으로 돌아가 실제 영향도 확인합니다. 저장과 작업 재개, 외부 앱에 의한 재생성은 보장하지 않습니다.

## 알림과 진단

`wrg configure-alerts`로 선택한 외부 채널을 설정하고 `wrg test-alert --channels <channel>`로 명시적 수신 시험을 합니다.
Web Push는 해당 브라우저의 권한과 시스템 Python cryptography가 필요합니다.
화면의 등록 완료는 브라우저 구독과 서버 등록이 일치한다는 뜻이며 실제 알림 수신 증거는 아닙니다.
서버 등록 실패 때는 기존 구독을 사용해 다시 등록할 수 있습니다. 서버 키가 바뀌거나 구독이 만료되면 화면의 재등록 동작을 사용하세요.
상시 Guard의 사건 알림은 수집과 별도 worker에서 전달하며 기기/수신처별 오류를 기록합니다. 수동 `test-alert`·단발 보고서는 전달 시험/현황 용도이고 경보 사건을 새로 만드는 기능은 아닙니다.
`wrg doctor`는 설치 사본·의존성·WSL 조건 진단에 사용합니다.
